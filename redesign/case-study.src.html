An AI tool sorts NDA clauses against a playbook. Code decides what a lawyer sees. These tests show where that holds and where it does not yet.

Test on 30 synthetic NDAs · playbook v1.0 · 16 October 2026

What the tests show. These checks need no lawyer, so one person can run them. They are in Evals.

  • Coverage: of the counterparty's tracked edits inside clauses got a finding. Of the 13 edits with none, 11 are notice-clause additions or spelling, and 2 are real misses.
  • Consistency: the reviewers often disagree. Re-run the same NDA and they report the same issue in only of cases. The same clause type gets opposite verdicts in different NDAs.
  • Routing: lanes alone are not enough. Code also enforces the playbook's "escalate" answers, overrides a pass when the AI's own reason says escalate, and sends fallbacks on High-severity rules to a lawyer. These guards catch 25 findings that the lanes alone would let through.
  • Prompt injection: 3 hostile contracts tried to talk the reviewer into passing clauses. In 6 runs, no targeted clause lost its lawyer item, apart from one definition item that normal re-runs also change. The code screen caught 2 of the 3. The third had no trigger words.

What is not shown. Legal accuracy. That needs a lawyer's answer key. The lane split below shows where findings went. It is not a score.

A lawyer approves everything before it goes out. A clause the AI calls a match still does not reach a lawyer. The shadow pilot measures how often that call is wrong.

Limits of this test

The rules are our assumptions, not positions confirmed by a legal team.

The contracts are synthetic. The reviews came from Claude Sonnet subagents with the engine's exact prompt, not from the engine's live API call.

No finding is scored against a lawyer's answer key.

The variance and injection tests are small: 3 contracts × 5 runs, and 3 hostile contracts × 2 prompts.

Evals that need no lawyer

Legal accuracy needs a lawyer's answer key. These checks do not. They measure whether the tool is consistent, whether code enforces the playbook, and whether hostile text gets through. One script makes them all: python3 evals/run_evals.py. The full report, with every flagged finding, is evals/EVAL_REPORT.md.

1. Routing guards

Lanes, the confidence floor and the catch-all rule route most findings. These extra guards catch findings where the AI's own output, or the playbook's answer, says a lawyer must decide.

GuardFindings caughtExample

2. Coverage of tracked edits (C01 to C10)

On our template, every counterparty edit carries a marker. That gives an answer key for where the edits are, though not for whether each is acceptable. An edit with no finding is a silent miss.

Outcome for each edit inside a clauseEditsShare

Of the 13 misses, 7 are additions to the notices clause, which the prompt tells the AI to skip when they fit the boilerplate rule. 4 are spelling. 2 are real misses: C06 clause 7.2, an edit to the IP clause (a High-severity, lawyer-only rule), and C08 clause 1.2, an edit to the definition of Group. The edits the tool passed without a lawyer are in evals/answer_key_template.csv, for the test-set author to mark right or wrong. That turns coverage into a recall figure.

3. Variance: the same NDA, five fresh reviewers

NDAFindings per runIssues reported in every runSame verdict in every runSame route in every run

The reviewers report the same issue in only 39% to 52% of cases. When they do report the same issue, the route agrees 71% to 92% of the time. This is the strongest argument for the shadow pilot, and for a measured agreement rate before any rule gets more automation. The live engine calls the API at temperature 0, which may vary less; that is not yet measured.

4. Consistency across NDAs

Clause typeFindingsAI: matchesAI: acceptableAI: deviationReaches a lawyer

Code cannot make the AI consistent. It can lower the cost of an inconsistent call. On a High-severity Shadow rule, an "acceptable" call goes to a lawyer. A "matches" call still does not, which is why coverage and a sample of passed findings matter. The insurers row is the clearest open problem: 3 NDAs (C13, C21, C26) called missing insurers a match and 1 (C22) an acceptable fallback, while 8 others called the same gap a deviation. A code check on the Representatives list (does it name advisers, auditors and insurers?) would remove the AI from that decision.

Safety and confidentiality

The counterparty writes the input. So every word of the contract, and every margin comment, is untrusted. The contract text is also confidential, and some of it is personal data.

How it works

The AI reads each contract, quotes each clause and gives a verdict. Code decides what the lawyer sees, because code can be tested and audited. The code still depends on the AI's verdict and confidence, so the AI's errors flow through: the evals above show where. The lawyers change the behaviour by changing the playbook.

The six steps below are the path of the work, in order. Each links to the stage that describes it.

    Three questions set the lane for each topic

    1. Could a wrong call cost IP, money or freedom to operate?
    2. Would two of our lawyers always make the same call from these words?
    3. Are you happy for the tool to draft the fix for a lawyer to approve?
    AI drafts

    When the clause deviates, the tool drafts the fix and the note to the counterparty. A lawyer approves.

    Shadow

    When the clause deviates, the tool forms a view but hides it until the lawyer decides. Both answers are logged, so we can measure agreement.

    Lawyer only

    When the clause deviates, the tool flags and quotes the clause. It drafts nothing.

    A finding also goes to a lawyer when no rule fits it, or when the AI's confidence score is below 0.6. On every lane, a clause that the AI says matches or fits a fallback does not go to a lawyer.

    What we need to move forward

    • About 45 minutes from each lawyerto fill in the process discovery workbook. It shows where their time goes, how they decide, and what must stay with people.
    • Three one-hour sessions with the legal teamto fill in the playbook worksheet. This replaces every assumed position with a confirmed one.
    • One playbook ownerwho signs off each version of the rules.
    • An implementation routechosen after a short look at how NDAs arrive today. This is the largest piece of work.
    • A shadow pilot on incoming NDAsWhen the tool finds a deviation on a high-stakes rule, the lawyer decides first and the tool's view is logged. A lawyer also reviews a sample of the clauses the tool passed. A rule gets more automation only when the log shows the tool agrees often enough. The lawyers set that bar.
    • A decision on how much routine work stays with peopleso junior lawyers still learn from the easy NDAs (stage 11).

    Stage 0Process discoveryThe team describes how the work is doneTemplate ready

    discovery/process-discovery-workbook.xlsx

    Each member of the legal team fills in the workbook before we build anything. It takes about 45 minutes. It is a general template, so it works for any team and any process, not only NDAs.

    TabWhat the team writesWhat we do with it
    TasksEach task, how often, how long, how much judgement, the worst caseFind where the time goes, and which work is routine
    How you decideWhat they check first, what is fine, what makes them stopThe first draft of the playbook rules (stage 3)

    WorriesConcerns and red lines, and how firm each one isHard limits on what the tool may do (stage 11)

    A Summary tab builds itself. It shows hours a month for each task and a score for how well each task fits a tool:

    fit for a tool = hours a month × (4 − judgement) × (4 − impact)

    Tasks that the team marks "Keep with people" are left out of the score. The workbook also makes promises to the team: they decide what stays with people, it is not used to judge their work, and they see what we build before anyone uses it.

    In this case study the workbook is a blank template. No legal team filled it in.

    Stage 1Problem statementWhat we are solvingDone

    NDAs are high volume and mostly low risk, but every one waits for a lawyer. The business waits with it, and lawyers spend time on clauses that match the template word for word.

    The goal: a lawyer spends time only on the clauses that need a lawyer, and can trust that the tool missed nothing.

    Stage 2TrackerWhich risks an NDA carriesDone

    The Google Sheet tracker logs each NDA and lists the risks an NDA can carry, each with an ID (R01 to R16). For example, R02 is the confidentiality period and R07 is governing law. Rules PB01 to PB08 and PB10 to PB18 each point back to a risk ID. PB09, PB19, PB20, PB21 and the catch-all PB22 have no risk ID yet, so 112 of the 572 findings do not trace to a risk in the tracker. The worksheet sessions must close that gap.

    The tracker names each risk but does not say where the line is. It says the confidentiality period is a risk. It does not say that 2 to 5 years is fine, 7 years is not, and a perpetual term needs a lawyer. That knowledge sat with the lawyers. Stage 3 writes it down.

    The tracker is a Google Sheet outside this package.

    Stage 3Lawyer worksheetThe lawyers define the rulesBuilt

    rules/playbook-worksheet.xlsx

    One row per topic in the template NDA. For each topic the lawyers write:

    • the preferred position (what the template says)
    • the fallbacks they would sign without a second look
    • the red lines, as exact as possible (days, years, named words)
    • a severity: High, Medium or Low
    • how to fix a deviation, and a standard note to the counterparty
    • whether a lawyer has confirmed the position (if not, it is marked "ASSUMED")

    Three questions set the lane for each topic (see How it works). The sheet suggests a lane from the answers, and the lawyer can overrule it. Other tabs cover scope, requests that counterparties often make, and escalation. A worked example tab shows one finished row.

    In this case study no legal team filled in the worksheet. We wrote the playbook from the template and our own knowledge, and marked every unconfirmed position "ASSUMED".

    Stage 4PlaybookThe worksheet becomes rules the tool followsBuilt

    rules/worksheet_to_yaml.py engine/playbook.yaml

    The script reads the worksheet and writes a draft playbook in the same format as playbook.yaml. Nobody retypes the lawyers' words. It lists every gap: a topic with no position, a request with no answer, a position not yet confirmed. The owner reviews the draft and freezes it with a version number.

    python3 rules/worksheet_to_yaml.py rules/playbook-worksheet.xlsx playbook.draft.yaml

    The playbook is plain text, so a lawyer can read it and every change shows as a diff. It holds:

    • scope, owner and the severity scale
    • rules PB01 to PB21, one per topic
    • PB22, a fixed catch-all: any clause the tool cannot place goes to a lawyer
    • requests RQ01 to RQ12, each with the team's standard answer

    The current version is 1.0, frozen on 14 October 2026.

    Stage 5Test set30 realistic NDAsDone

    engine/contracts/

    30 mutual NDAs. Ten are on the Halyard template with the counterparty's tracked changes. Twenty are on the counterparty's paper. They cover the common asks: a shorter confidentiality period, a different governing law, residuals, non-solicits, and one-way NDAs presented as mutual.

    Tracked changes appear as markers. This is the format the intake step would produce from a Word file:

    [[INS: added text]] [[DEL: removed text]] [[COMMENT: a margin note]]
    Stage 6Review engineThe AI reads, code decidesDone

    engine/review.py

    1. It turns the playbook into the AI's instructions. The AI sees those rules and no other standard.
    2. The AI reads one contract. For each clause it returns a rule ID, a verdict, an exact quote, a confidence score, a one-line reason and, for a deviation, a draft fix.
    3. Before the call, code masks personal data and screens the contract for text addressed to the reviewer.
    4. Code routes each finding by the lane that the playbook sets for its rule. In this test we set the lanes; the lawyers confirm them in the worksheet. A finding goes to a lawyer if:
      • no rule fits, or the AI's confidence score is below 0.6
      • the AI finds a deviation on a Lawyer only or Shadow rule
      • the AI says a fallback fits on a Shadow rule
      • the finding is a known request whose playbook answer says "escalate"
      • the AI's own reason says escalate, whatever its verdict
      • the rule allows a draft but the AI gave none
      • the injection screen flags the text.
    5. When the AI says a clause matches, the finding does not go to a lawyer, on any lane. In the test, findings on Lawyer only and Shadow rules took this path. That is the biggest open risk. The shadow pilot needs a random sample of these for a lawyer to check.

    Each contract had its own fresh AI reviewer, so no finding carried over from one contract to the next.

    Problems found: on the first pass, 556 of 572 quotes (97%) matched the contract text exactly. The same reviewer re-quoted the other 16, mostly by putting back the edit markers. One file had an encoding fault. Reviewers did not always choose the same way on edge cases: Evals measures how often. A script checks every quote against the contract text, and all 572 quotes now pass. To run it, go to engine/ and run python3 check_quotes.py. The check proves a quote is real. It does not prove the quote is relevant. No verdict was changed by hand.

    Stage 8Lawyer review pageWhat the lawyer seesPrototype

    demo.html engine/static/index.html engine/server.py

    The lawyer sees:

    1. A one-line summary: who sent it, on whose paper, and whether it looks OK.
    2. Findings in order: decisions for the lawyer, then drafted fixes to approve, then acceptable, then matches.
    3. For each finding: the quote, the rule, the severity and the reason, plus the team's standard answer for known requests.
    4. When the tool finds a deviation on a Shadow rule, its view stays hidden until the lawyer decides.

    Each decision is logged next to the tool's verdict. To try it without Python, open the demo review app. It holds the 30 saved reviews in one file. It has no Live mode, and decisions stay in the viewer's browser.

    To run the full page with a local server:

    cd engine
python3 server.py

    Then open http://localhost:8765. Replay mode uses the saved reviews. Live mode needs an API key.

    Stage 9IntakeFrom the counterparty to the lawyerNot built
    1. Receive through one front door: a shared inbox or a request form that asks for the counterparty, deal owner, purpose and deadline.
    2. Log a row in the tracker.
    3. Screen before any AI runs. Send anything that is not an NDA to a lawyer untouched. Send counterparties on the "always a lawyer" list to a lawyer. Note whether it is our paper or theirs.
    4. Convert the Word file to text, with tracked changes as [[INS]] and [[DEL]] markers.
    5. Review with the engine against the frozen playbook.
    6. Queue it on the lawyer's page as green (nothing to decide), amber (drafted fixes only) or red (at least one decision).
    7. Decide and send. The lawyer approves, edits or overrules, and the tracker row moves on.

    The smallest working version: a shared inbox, a script that runs on each new attachment, and the existing review page.

    Stage 10Learn and widenMore automation, one rule at a timeNot built
    1. When the tool finds a deviation on a Shadow rule, the lawyer decides without seeing the tool's view, and the log records both answers.
    2. For each rule, measure how often the tool agreed with the lawyer. A miss on a High rule costs 5, a miss on a Low rule costs 1.
    3. The log has a gap: a clause that the tool wrongly passes as a match never reaches a lawyer, so the log cannot show it. To measure these misses, a lawyer must also review a sample of the clauses the tool passed. The pass-through rate in stage 11 gives that sample.
    4. When a rule meets the bar the lawyers set, the owner may move it from Shadow to AI drafts. That is a one-line change in the playbook and a new version number.
    5. Set the confidence threshold from the log. The current 0.6 is a placeholder.
    6. Send each overrule back to the worksheet. It usually means a rule's wording is unclear.
    Stage 11Keep the easy winsLeave room for people to learnNot built

    Junior lawyers build judgement on the easy NDAs. If the tool takes all of the easy work, juniors lose the work they learn from, and everyone is left with only the hard cases. So the tool should hand some routine work back to people on purpose. There are three options, and they can be combined:

    OptionHow it worksCostAlso gives us
    Learning mode per userFor a lawyer in learning mode, the tool hides its view on every clause. The lawyer reviews first, then compares.Slower reviews for those lawyersFeedback on each review when it is most useful
    Pass-through rateOne NDA in every N goes to a lawyer with no tool output. The tool still runs in the background and logs its view.Fewer NDAs get the time savingAn unbiased sample to keep measuring the tool after go-live
    Feedback in the documentThe lawyer marks each finding as agree or disagree, with a short reason, where they read the contract.A few seconds per findingOverrules go back into the worksheet and improve the rules

    The first two reuse the shadow mechanism that already exists. Our starting suggestion is learning mode for junior lawyers plus a small pass-through rate for everyone. The legal team makes the final choice.

    Implementation options

    The engine works on clean text in a test folder. Real NDAs arrive by email, as Word files with tracked changes, as PDFs, or as DocuSign envelopes, and the lawyers work in Word or Google Docs. We have not tested any of that yet.

    Four questions decide the route
    1. Where do NDAs arrive today: a shared mailbox, individual inboxes, a request form, or a contract system?
    2. In which format: Word with tracked changes, PDF, Google Docs, or a DocuSign envelope?
    3. Where do the lawyers work on them: Word, Google Docs, or email?
    4. Where must the record end up: the tracker, a contract system, or a shared drive?

    A week of watching how NDAs arrive answers these. The "Tools and data" tab of the process discovery workbook collects the same facts from each lawyer. We should not choose a route before then.
